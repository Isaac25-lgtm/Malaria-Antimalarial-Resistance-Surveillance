# The synthetic demo dataset

A compelling presentation must never depend on live sensitive data. This
dataset lets the whole national → district → facility → signal → explanation →
action journey be walked safely, with a small number of deliberately planted
storylines and one district where nothing is wrong.

It is generated by `mars-demo-dataset` and lives in
`backend/src/mars/demo/`.

## What it is, and what it is not

Every facility, patient, identifier and clinical detail is **fictional**.

- Facility codes carry the `DEMO-HF` prefix and every facility row is marked
  `is_synthetic`.
- Patient identifiers carry the `SYN` prefix. No real scheme issues values with
  it — a synthetic identifier that looks real is the one that ends up in an
  email.
- **No facility has a coordinate.** A plausible point on a fictional facility is
  exactly the detail that escapes a demo and gets believed.
- The source system is `mars-demo-ereg`, so a row in a log, a quarantine table
  or a screenshot is instantly recognisable as demo data rather than a leak.

**Districts and subcounties are real.** The generator invents no administrative
unit: it resolves them from the imported Uganda hierarchy, and stops with an
error if that hierarchy is not there. A demo on fabricated districts cannot be
navigated on the real map and teaches an audience to trust a map that is wrong.

Which real district plays which storyline is a **demo fiction**. It describes
nothing about that district, and the manifest says so in writing.

**Nothing here is Lane B.** Every storyline is routine-derived. A storyline may
produce a surveillance signal. None of it is, or can become, a confirmed
antimalarial resistance finding — that is established externally, by a reference
laboratory, under separate governance.

## It loads through the real pipeline

The generator writes **inbound-contract artefacts** (JSON Lines, the contract in
`docs/data-dictionary/ereg-inbound-contract.md`), not database rows. The demo
therefore passes through the same ingestion pipeline, the same validator and the
same database constraints as real data.

That is the point. A generator that wrote straight into `mars_core` would prove
nothing about the system it demonstrates, and the dataset would quietly drift
into a shape real data can never take.

A small share of rows is **deliberately invalid** — a code outside the value
set, a number with no unit, a result recorded with no test, a row with no date.
They are quarantined by the ordinary path, so the quarantine screen has
something in it. A demo where every row is clean teaches the wrong expectation
of real data.

## Determinism

The same seed produces **byte-identical** artefacts. No wall-clock time and no
unseeded randomness appear anywhere in the generator; even the envelope's
`extracted_at` is derived from the register month.

This matters because the dataset is also the golden fixture that later detector
work is measured against, and a fixture that changes under you is not a fixture.

## The storylines

Declared in `backend/src/mars/demo/storylines.py`, each with what the generator
plants, what MARS should surface, and — the half that matters — what MARS
**must not** conclude. A detector that fires on the control district is worse
than one that fires on nothing.

| Storyline | Planted | The trap it sets |
| --- | --- | --- |
| Repeat-positive cluster | Patients testing positive two or three times within 42 days at one facility, each visit with a full antimalarial course | Concluding resistance from routine data |
| Testing anomaly | RDT testing falls sharply for six weeks; attendance, fever reporting and positivity are unchanged | Reporting the resulting case decline as an improvement |
| Completeness artefact | Two facilities report nothing for the first half of the period, then start | Reading the district total's rise as epidemiological |
| Spatial cluster | Repeat positives concentrate in two adjacent subcounties while the district total stays flat | Plotting household points, or reporting an area below the minimum count |
| Seasonal control | A gradual rise with stable testing, positivity and completeness | Alerting merely because counts are high |

Each planted repeat-positive visit records a full antimalarial course. Without
that, the pattern has an ordinary explanation — the patient was never treated —
and the storyline would prove nothing.

The completeness storyline works by **silence**, not by zeros: a facility that
is not reporting sends nothing at all. Sending zeros is a different and much
rarer real-world situation, and conflating the two is the mistake the storyline
exists to expose.

## Running it

```
# 1. The geography must already be imported.
mars-import-geography --data-dir <dir>

# 2. Write the artefacts, the facility register and the manifest.
mars-demo-dataset generate --out-dir demo/

# 3. Create the fictional facilities.
mars-demo-dataset register --out-dir demo/

# 4. Load, through the ordinary ingestion path.
for f in demo/batches/*.jsonl; do mars-import-encounters load --file "$f"; done

# When finished.
mars-demo-dataset purge --confirm
```

`generate` accepts `--district CODE` (repeatable — storylines are assigned in
the order given), `--seed`, `--start`, `--end`, `--facilities-per-district` and
`--daily-attendance`. Without `--district` it takes the first districts in the
hierarchy by code.

`purge` is scoped by the demo facility-code prefix and the demo source system,
and by nothing else. A purge that took a date range or a district would
eventually be pointed at real data.

## Output

```
demo/
  manifest.json      the storylines, the counts, and the warnings above
  facilities.json    the fictional facility register
  batches/           one JSONL artefact per facility per month
```

`manifest.json` is machine-readable and its storyline keys are stable: later
work reads them to check a detector against what was actually planted.
